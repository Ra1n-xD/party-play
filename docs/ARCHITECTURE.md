# PartyPlay — архитектура платформы

## Назначение

PartyPlay — npm-workspaces монорепозиторий с общей платформой комнат и
независимыми игровыми модулями. Платформа отвечает за каталог, места,
подключения, сессии, хоста, ботов, зрителей, реконнект, паузу и доставку
состояния. Конкретная игра отвечает только за свои правила, закрытое состояние,
проекции и игровые команды.

Одна комната создаётся для одной игры. Её `gameId` задаётся при создании и
больше не меняется.

Корневые файлы старого «Бункера» на сервере и старые клиентские экраны
сохранены как совместимые точки импорта. Канонические платформенные входы
находятся в `platform/`, а игровые адаптеры — в `games/<gameId>/`.

## Общий типизированный контракт

`GameContractById` связывает идентификатор игры с пятью типами:

```ts
interface GameContractById {
  bunker: {
    settings: null;
    publicState: BunkerPublicState;
    privateState: BunkerPrivateState;
    command: BunkerCommand;
    event: BunkerEvent;
  };
  durak: {
    settings: DurakSettings;
    publicState: DurakPublicState;
    privateState: DurakPrivateState;
    command: DurakCommand;
    event: DurakEvent;
  };
  uno: {
    settings: UnoSettings;
    publicState: UnoPublicState;
    privateState: UnoPrivateState;
    command: UnoCommand;
    event: UnoEvent;
  };
}
```

Из этого отображения выводятся `RoomSnapshot<G>`,
`RoomCommandEnvelope<G>`, настройки и игровые проекции. Клиент и сервер не
передают произвольные игровые payload без повторной runtime-проверки на
сервере.

Серверный `ServerGameModule<G>` предоставляет платформе:

- ограничения мест и настройки;
- жизненный цикл `lobby | playing | results`;
- разбор и выполнение игровой команды;
- старт и повторную игру;
- публичную и приватную проекции;
- реакцию на паузу, смену контроллера и исключение места;
- очистку таймеров и отложенных действий при удалении комнаты.

Клиентский реестр хранит метаданные каталога, обложку, ограничения мест и
лениво загружаемый корневой компонент игры.

## Комната, место и контроллер

Платформенная комната хранит неизменяемый `gameId`, настройки выбранной игры,
фиксированный лимит мест, ревизию, места, зрителей и game-specific runtime.

Место и текущий контроллер различаются:

- `owner` сохраняет постоянного владельца — человека или постоянного бота;
- `controller` показывает, кто действует сейчас: человек, бот или никто;
- временный бот получает то же место и то же игровое состояние;
- возврат авторизованного владельца меняет только контроллер и его epoch;
- закрытое место нельзя восстановить или занять повторно.

Игровая информация места находится в runtime соответствующего модуля.
Платформа не должна читать чужие руки, карты персонажей или правила ходов.

## Последовательность команды

```text
клиент
  → RoomCommandEnvelope(gameId, commandId, expectedRevision)
  → executeInRoom(roomCode)
  → runtime-проверка envelope, роли, gameId и revision
  → platform command или module.parseCommand()
  → server-authoritative переход
  → одна новая revision и снимки получателям
```

Команды одной комнаты выполняются последовательно. Принятая команда
запоминается по участнику и `commandId`; её повтор не изменяет состояние.
Устаревшая ревизия отклоняется, а клиентская FIFO-очередь может один раз
повторить ту же команду с тем же `commandId` после свежего снимка.

## Проекции и приватность

`statePublisher` строит одну публичную основу комнаты и отдельную приватную
проекцию для каждого подключённого человеческого контроллера.

- Игрок получает публичное состояние и только приватное состояние своего
  места.
- Зритель получает то же публичное состояние и всегда
  `privateGame: null`.
- Постоянному или временному боту приватное состояние не отправляется по
  сети; серверный модуль передаёт его стратегии бота только вместе с
  публичной проекцией.
- Данные заявки на восстановление не открывают состояние комнаты до решения
  хоста.

## Пауза и восстановление

Причины паузы принадлежат платформе:

- ручная административная пауза;
- множество отключённых человеческих мест.

Игра возобновляется только после снятия последней причины. Модуль замораживает
точный остаток своего таймера и отменяет bot-delay. Reconnect, подтверждённая
замена, временный бот и исключение проходят через последовательный executor
комнаты. Callback таймера или бота повторно проверяет идентификатор партии,
хода и epoch контроллера, поэтому устаревшее действие становится no-op.

При отключении хоста роль детерминированно переходит следующему подключённому
человеку и автоматически назад не возвращается.

## Игровые модули

### Бункер

Адаптер «Бункера» сохраняет существующие фазы, правила, ботов,
административные действия и legacy Socket.IO-события. Он переводит текущее
состояние в общий контракт без переписывания игрового движка.

В общем серверном `Player` пока остаются несколько полей «Бункера»
(`character`, reveal/vote flags и другие). Это осознанный слой
совместимости, а не API для новых игр. Новый модуль не должен использовать
эти поля; их можно вынести в отдельный runtime последующей узкой миграцией.

### Подкидной дурак

«Дурак» хранит серверное authoritative-состояние 36 карт отдельно от
платформенных мест:

- руки, колоду, стол, отбой и удалённые рубашкой вверх карты;
- круговой порядок, сдающего, атакующего, защищающегося и очередь
  подкидывания;
- точный этап боя, лимит атаки и результат;
- идентификатор решения и замороженный/активный таймер.

Игровые переходы проверяют команду заново против текущего состояния. После
каждого принятого перехода все 36 уникальных карт находятся ровно в одной
закрытой зоне. Планировщик только ставит timeout и bot-delay; правила
тайм-аута и хода остаются в движке.

Бот выбирает действие только из общей публичной проекции и приватной руки
своего места. Он не получает чужие руки и будущий порядок колоды.

### UNO

UNO хранит отдельно от платформенных мест классическую колоду из 108 уникальных
карт, руки, сброс, направление, активный цвет и очередь участников. Сервер
атомарно проверяет розыгрыш карты и выбранный цвет, управляет добором,
перемешиванием сброса, действием специальных карт и завершением одной раздачи.

Окно вызова UNO и решение по Wild Draw Four — независимые публичные pending-
состояния. Поэтому пропущенный вызов можно поймать до принятия или challenge
Wild Draw Four. Законность Wild Draw Four фиксируется только во внутреннем
runtime в момент хода и никогда не попадает в публичную или чужую приватную
проекцию. Клиент и бот получают от сервера только разрешённые им действия;
боту дополнительно доступна исключительно собственная рука.

Таймер, пауза, смена контроллера, исключение места и повторная партия используют
те же lifecycle hooks, что и остальные модули. Отложенные действия проверяют
идентификатор партии, хода, pending-решения и epoch контроллера перед
выполнением.

## Добавление игры

1. Добавить типы в `shared/games/<gameId>/types.ts` и строку в
   `GameContractById`.
2. Реализовать `ServerGameModule<gameId>` и зарегистрировать его на сервере.
3. Реализовать клиентский корневой компонент и зарегистрировать метаданные и
   обложку.
4. Хранить правила и контент в самом игровом модуле; расширять платформу
   только для действительно общих возможностей.
5. Проверить публичную/приватную границу, повторные и устаревшие команды,
   disconnect/reconnect, паузу, зрителя и повторную игру.

## Технологии и проверка

- Node.js, Express и Socket.IO на сервере;
- React 18 и Vite на клиенте;
- TypeScript и npm workspaces;
- in-memory комнаты без отдельной базы данных.

Основные команды проверки:

```bash
npm run build
npm run format:check
git diff --check
```
